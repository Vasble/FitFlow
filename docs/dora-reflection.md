# Завдання 5. DORA-рефлексія

### Deployment Frequency

CI/CD pipeline (задача T-01) автоматично збирає й розгортає кожен злитий приріст на staging, а завершення спринту раз на 2 тижні дає гарантований реліз на прод. Це проміжний рівень — до Elite (кілька релізів на день) команда може наблизитися, впровадивши feature-флаги й розгортання одразу після проходження Review, не чекаючи кінця спринту.

### Lead Time for Changes

Дрібні, оцінювані в годинах задачі (T-02…T-06a) проходять дошку швидко, а обов'язкова колонка Review з Code Review не дає задачам застрягати без зворотного зв'язку. Чим менша задача, тим коротший час від коміту до потрапляння в реліз — саме тому вимога «дрібна, оцінювана задача, а не «зробити бекенд»» напряму скорочує Lead Time.

### Change Failure Rate

Definition of Done вимагає пройденого Code Review, автотестів і перевірки за критеріями прийнятності (AC) перед тим, як задача потрапить у Done — це відсіює частину дефектів ще до релізу. Окремо виділена мітка Bug з пріоритетом Critical/High дозволяє команді бачити й блокувати реліз, поки такі дефекти відкриті.

### MTTR (Mean Time to Restore)

План підтримки (SLA) і Changelog з фази «Супровід» фіксують, яка версія працює в проді й що в ній змінилося, а CI/CD pipeline дозволяє швидко відкотитися на попередню стабільну збірку. Мітка DevOps на дошці виділяє задачі інфраструктури окремо, тому інцидент, пов'язаний з розгортанням чи турнікетом, одразу видно й можна пріоритезувати без плутанини з фічами.
